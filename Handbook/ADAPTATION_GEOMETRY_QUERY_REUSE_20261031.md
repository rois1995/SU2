## Boundary smoothing extension — user specification (verbatim)

Yes—smoothing needs attention, but much of its cost is the same geometry bottleneck. The sampled call chain was:

SmoothBoundary → GeometryGuidanceExcess → surface-union certification

Those timings overlap; they are not separate costs to add together.

The main agent should include smoothing in the same connected optimization:

- Measure work per useful move: candidate positions tried, metric/geometry rejections, expensive certificate calls, accepted moves and whole-patch debt reduction.
- Reuse the unchanged star context: connectivity, boundary support, old-side scores and valid certificates. Position-dependent metrics and changed geometry still need fresh evaluation.
- Reduce expensive candidate evaluations: improve candidate ordering and use valid inexpensive bounds before full certification. Some screening already exists, so target the remaining measured repetition.
- Avoid repeatedly searching unchanged rejected stars: any reuse must depend on the complete cavity state and be invalidated when relevant neighbors change.
- Judge smoothing by debt reduction per second, not merely accepted-move count.

The latest whole-patch merit correction addresses which moves are useful. It has not yet established that finding and certifying those moves is efficient.

I would therefore ask the main agent to optimize boundary smoothing together with its geometry-query path, then measure interior smoothing separately. Blanket reductions in trial counts or disabling boundary movement could make execution faster while preventing the mesh from reaching the unchanged gates.
