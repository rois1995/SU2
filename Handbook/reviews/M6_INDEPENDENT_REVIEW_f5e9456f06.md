## A. Findings ranked by importance

### 1. The actionable blockage is local construction/certification, not yet partition balance — HIGH CONFIDENCE

The final M6 workflow is unaccepted and has no accepted return mesh/solution transfer (`M6_DIAGNOSTIC_DECISION.md:35–49`, `diagnostic55/observed/status.json`). The independently checked witness calculation establishes a narrower fact: several **positive-orientation** candidates violate the metric shape thresholds; it does **not** establish full geometric validity, absence of outside intersections, complete dependency coverage, or eventual repair feasibility. The checker recomputes centroid quality on original-tetrahedron P1 sensor fields but does not certify complete metric-edge integration or physical contacts (`diagnostic55/witness_analysis.py:25–60, 71–104`).

**Edge 23754–24333 (rank 2):** initial old patch 2 cells, full-patch min `q=0.232448`, `J=0.062308`; proposed 4 cells, min `q=0.183971960`, `J=0.042789630` (production first failed cell 3970075). The first proposal therefore fails **both** strict q ≥ 0.20 and J ≥ 0.05, despite positive orientation. A later snapshot for the same edge has 5 old cells and 12 stored fresh records, but `geometry_candidate=false` with *cannot see retained skin*. The stored `fresh` may be partial/stale and cannot be treated as a complete replacement (`observed/witness_rank2_{0,1}.json`, `witness_analysis.json`). The observed sizes are below 64-old/128-new-cell caps; **the unrecorded complete growth history prevents exclusion of other later caps**.

**Edge 81–17687 (rank 3):** the old 3-cell patch already has `J_min=0.039711` when evaluated against the target; the proposed 6-cell patch has `q_min=0.127630` and **`J_min=0.019287`**. Production reports `J=0.096230` because it stops on first failing cell 3946523. The whole-patch minimum J belongs to a different cell. This is not evidence of a q-only failure. This case probes an initially under-threshold target-metric configuration and is a useful contrasting witness (`observed/witness_rank3_0.json`; `witness_analysis.json`).

The native engine preserves `ShapeAdmission::Absolute` for production (`Common/src/adaptation/CNativeRemesher3D.cpp:452–454`); its `ValidityOnly` diagnostic alternative requires q>0, J≥0.001 **per intermediate step** (`Common/src/adaptation/CNativeMetric3D.cpp:167–184`; header lines 68–75). Neither variant removes the need for the **final global** q ≥ 0.20, J ≥ 0.05, metric-edge ≤ 1.8, geometry, contact, feature, source, first-height, and transfer contracts. Local *intermediate transaction* acceptance follows the existing `ValidateMetricChange` rules and may permit inherited oversized edges pending subsequent adaptations; record them rather than conflating the two certificates. The engine already has split reconstruction/refit and bounded growth/repair (`CNativeEngine3D.cpp:2563–2624, 2726–2775`), but the witness callback omits the actual ownership/version, complete external-contact context, and growth sequence (`CNativeRemesher3D_tests.cpp:485–529`).

### 2. Partitioning balances its **supplied proxy**, not measured CPU work — HIGH CONFIDENCE for proxy, UNVERIFIED for workload

Recomputed from committed `diagnostic55/baseline_records.json` (six `stage=partition` rows): original and migrated work sums **both equal 5,664,358**; max/mean changes **4.69910765 → 1.08448972**. The moved-cell count **102,883** is a *global* count repeated in each log, not six independent migrations. The current implementation uses one graph vertex per tetrahedron, a face-dual adjacency graph and `ParMETIS_V3_PartKway` with `ncon=2` and `(work, 1)` constraints, with 15% tolerance (`Common/src/adaptation/CNativePartition3D.cpp:15–45, 185–265`). Separate source-donor migration exists (`CNativeRemesher3D.cpp:321–388`). The code incrementally modifies imported tetrahedra; it is not a topology-independent mesher.

`diagnostic55/weights.py:29–52, 73–109` independently transcribes the current formula and matches only the **aggregate** 5,664,358, not an exported production weight at each cell. The replica's maximum of 591 and zero clipping at 1024 weaken clipping as an explanation **in the replica**; production per-cell equivalence has not been checked. The metric-mismatch descriptors are sound *illustrations* but have no held-out regional useful-compute labels, so no predictor is validated (`M6_WEIGHT_PREDICTORS.md:31–90`). Changes to weights, graph representation, or ParMETIS API are premature.

### 3. MPI call volume is real, but attribution and causal wait remain unknown — HIGH CONFIDENCE for measured MPI-wrapper time

The bounded replay reports about 670k wrapped calls per rank, of which **465,080 per rank** invoke the `CPassiveComm::AllreduceMax(unsigned long, communicator)` direct helper; that caller contributes 17.23–22.73 s/rank. Total wrapped MPI duration is **18.739–25.996 s/rank** over a **62.723-s** slowest rank (`diagnostic55/m6_mpi_callsites.csv`, `mpi_analysis.json`). `CDistributedSearch.cpp:440–458` confirms that `ElectFailure` uses this helper, but other sites do too. The PMPI tool records the *direct* return address, not its enclosing semantic caller (`diagnostic55/mpi_calls.c:24–72`); do **not** equate all AllreduceMax time with failure elections or all MPI duration with network transfer.

The collector covers 18 calls, not every MPI routine; nonblocking time outside calls is not attributed. PMPI_Wtime, hash-table aggregation and `dladdr` resolution introduce instrumentation effects (the latter happens after capture); six ranks have zero trace overflow. `plain/observed` counter agreement is useful but does not show byte-identical transaction traces. The single observed/plain pair took **62.723/89.999 s**, under `nice 19`, `--bind-to none` and shared-host contention; it cannot estimate measurement overhead. The report's **1.428×** quantity is only a conditional quotient (`62.723 / 43.925`) assuming zero wrapped MPI time and unchanged outside-MPI time; it is **not an optimization speedup ceiling** in the ordinary engineering sense (`M6_MPI_CRITICAL_PATH.md:27–80`). Useful local computation, collective entry skew, remote service latency and critical-path waits remain unresolved.

### 4. Evidence is bounded, selected and not independently executable from this checkpoint alone — HIGH CONFIDENCE

The 28 patches are a deterministic first-four-distinct-by-category/rank sample, all containing physical surface faces; none came from ranks 0–1 or captures late-M6 dominant ranks 4–5 (`CNativeRemesher3D_tests.cpp:485–499`, `M6_CONSTRUCTION_WITNESSES.md:15–28`). The 2,048-work-unit prefix stops before full adaptation/BL/transfer. An event on an early surface is a valid *construction counterexample*, not proven to be the cause of the late 1,800-s M6 deadlock/stall.

The pinned manifest, input SHA256 values, checkpoint changes and status receipts are internally coherent; the scripts explicitly check original node IDs/coordinates, SPD tensors and their saved round trip (`diagnostic55/prepare.py:48–74`, `run_manifest.json`). But the large original mesh, archived metric and authority sidecar are local and absent from the Git checkpoint/ZIP. I verified source and committed *reports/receipts*, not the actual binary input hashes, solver reconstruction, or new numerical measurements.

## C. One next experiment — state-complete **single-transaction capture and replay**

**Recommendation:** **Endorse the construction experiment, but narrow it to edge 23754–24333 first.** Treat 81–17687 as a contrasting *second* witness only after the first replay infrastructure is verified. This gives a cleaner initial q/J-compliant old patch for testing the exact admission obstacle, while the second starts with a preexisting J deficiency. Do not launch a new full M6 campaign.

**Hypothesis H1:** the current operator can reach an accepted final local replacement if permitted a bounded geometrically valid intermediate step, but strict *intermediate* shape admission prunes that route. **Alternatives:** (H2) retained-skin/interface geometry or missing/outdated dependencies; (H3) current cavity/topological search lacks a needed construction under current caps; (H4) metric progress/length, physical contact/source/height constraints block the result; (H5) MPI ownership/reservation or synchronization prevents otherwise admissible work. A local replay can discriminate H1–H4; H5 requires trace of the same original MPI transaction.

Treat any cap truncation as **missing evidence**, not a failed feasibility proof. If a limit conflicts with a code invariant, retain the stricter invariant. Inspect for the capture itself changing trajectories by comparing feature attempt IDs/reasons under diagnostic-off/on paths where feasible, without a large timing study.

## D. Loseille–Alauzet–Menier (CAD 85, 2017): applicability

**Reusable:** the natural-tetrahedron/target-metric-intersection workload decomposition into insertion/collapse/optimization terms provides a principled **candidate predictor**; compare against measured *regional useful-work labels* and the current proxy using held-out data. Their simultaneous surface/volume cavity thinking and obstruction-aware interface coverage support complete dependency capture; their staged processing of largely independent subregions suggests a later synchronization/scheduling avenue *if* current critical-path attribution supports it.

**Not directly transferable:** the paper's coarse-grained strategy temporarily fixes artificial partition boundaries and then **remeshes recovered interfaces in new partition levels**. This implementation uses fine-grained synchronized, versioned, cross-owner cavity transactions and does not have the corresponding independent-region completion and interface recovery infrastructure. Its kernel, per-operator costs, metric composition, curved geometry and contact checks differ. Published time or quality distributions do not establish native SU2's hard q/J/metric-edge gates, frozen sensor and source, first-row/BL constraints, conservative transfer, or M6 acceptance. The paper's metric formula is useful as a *hypothesis to calibrate*, not a license to replace the existing ParMETIS setup.

**Bottom line:** do **one small, complete-state construction replay** with gate-by-gate certification. Only after an accepted repair path is demonstrated should the team decide between a construction change and targeted MPI scheduling work. Weighted partitioning is already functional for its proxy and is not currently the critical engineering next step.
